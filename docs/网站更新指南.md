## 1. 新增观鸟活动

照片放入 `incoming/events/YYYY-MM-DD_地点/`，例如 `incoming/events/2026-11-14_La-Jolla/`（仅为命名示例，必须换成真实活动日期和地点）。

> 请只处理子文件夹（填写完整路径）：。请新增观鸟活动。日期：；地点：；路线：；组织者：；主要鸟种（我已确认）：；参加人数：；活动介绍：；总结：；照片文件夹：。请整理英文草稿，未知信息留空，用开发分支生成预览，未经确认不要正式发布。

数据模板：`content/templates/event.json`。由 Codex 将完整条目添加至 `content/events.json`。照片数组格式为 `[{"image":"incoming/events/YYYY-MM-DD_地点/文件.jpg","alt":"准确的英文图片说明"}]`。活动按日期从新到旧展示；缺少日期的排在最后。

## 2. 批量增加摄影作品

照片放入 `incoming/photography/日期、地点或摄影专题/`，例如 `2026-11-14_La-Jolla`、`San-Diego` 或 `Coastal-Birds`。

> 请只处理子文件夹（填写完整路径）：。请批量增加摄影作品。照片文件名与标题对应：；已确认英文鸟名和学名：；拍摄日期：；地点：；主题分类：；简短说明：。没有确认的鸟种不要识别或填写。请提供英文草稿与预览，不正式发布。

模板：`content/templates/photograph.json`；数据：`content/photography.json`。可一次添加多张，每张一条记录。现有摄影作品保留旧标题，但鸟名、学名、拍摄日期和地点保持空白。主题可用 Coastal、Wetlands 等你确认的类别。点击图片或键盘 Enter 放大，Esc 关闭。

新作品图片放入 `incoming/art/作品名称/`，例如 `incoming/art/Golden-Pool/`。

> 请只处理子文件夹（填写完整路径）：。请新增或更新艺术作品。作品名称：；图片：；创作说明：；分类（design/painting）：；Redbubble 链接：；Etsy 链接：；需要删除的旧链接：。请保留其他内容，不抓取价格和折扣，生成预览，不正式发布。

模板：`content/templates/artwork.json`；数据：`content/art.json`。商品链接结构为 `[{"url":"https://...redbubble.com/..."},{"url":"https://www.etsy.com/..."}]`，删除链接后从对应数组移除即可。没有准确的作品购买地址时不自动拼接；现有 Redbubble 总店链接单独保留。

## 审核与发布

Codex 会把新增内容加入对应栏目；只有填写真实 `updatedAt` 日期的已公开条目进入首页 Latest Updates。旧内容迁移不虚构更新日期，因此初始 Latest Updates 显示提示语。

检查英文、日期、鸟名、照片版权和购买链接。确认无误后明确说“批准将这个预览版本发布到正式网站”。此前只在开发分支和预览中工作。

技术维护：Node 24 LTS，首次运行 `npm ci`，之后 `npm run build` → `npm run check` → `npm run preview`，打开 http://127.0.0.1:4173。修改数据后重新构建即可。Vercel 沿用 `npm run build` 和 `dist`，自动安装 sharp 图片处理依赖。原照片仅供本机预处理，incoming 已被 Git 忽略，不上传 GitHub 或 Vercel。Codex 先运行 `npm run prepare-content -- --folder "incoming/分类/本次子文件夹"`（普通构建不会自行选择或扫描原图），生成去 EXIF、最长边 1600 的网页图至 `assets/uploads/`，自动更新数据引用，再将网页图、数据文件和 `content/media-registry.json` 处理记录一起提交。Vercel 取得这些已提交的网页图后，生成 480/1600 展示版本到 dist 并部署。dist 无需进入 GitHub；不能只提交数据而漏掉 assets/uploads。旧 assets 中原有的已跟踪图片保留，本规则适用于以后放入 incoming 的照片。

若启用 GitHub 自动预览，开发分支推送后在 Vercel 项目 Deployments 中打开对应 Preview；不要点击 Promote to Production。未核实 Vercel Production Branch 前不要盲目推送。

## 以后每次更新

1. 你只需在当前项目放入照片，并发中文指令。
2. Codex 同步远端、处理图片、整理英文与数据，运行检查，提交数据及网页图到开发分支，提供对应 Vercel Preview。原图继续留在本机，请自行备份。
3. 你审核并明确批准后，Codex 才将审核过的版本合入 main，验证正式部署。首次发布会包含本次基础升级；以后每次仍先检查 main 是否有其他更新。

此流程需要 GitHub SSH 与 Vercel 连接仍可用。它由 Codex 执行，不是放照片后自动发布；不需要你手动编写代码或上传优化图片。

## 子文件夹与防止重复导入

每次必须在中文指令中写明一个完整的子文件夹路径，不能只说“处理 incoming 中的照片”。可以使用中文文件夹名；需要空格时由 Codex 正确处理。观鸟日期未知时先确认，不编造日期。子文件夹内部可继续分类，但不处理其他批次。

Codex 只为指定文件夹内、你确认要使用的图片建立内容条目；脚本不会自动遍历所有素材加入网站。未选中的照片可以留在原处。普通构建只使用已经准备好的网页图；若数据还引用未指定文件夹的原图，构建会提醒，不能悄悄批量处理。

处理记录保存在 `content/media-registry.json`，记录图片指纹、原路径、处理时间、网页图片和所属内容。复制或改名的同一张照片不会因此变成新照片；重复新增会被阻止，应该更新已有条目。若你明确要求把同一张照片用于另一篇活动或栏目，Codex 才会通过受控复用使用同一网页图。系统能比较文件内容及标准化后的网页图，不承诺识别所有裁剪、重修或相似照片。

现有网站的 9 张作品图片已纳入初始索引，避免把原网站已有图片重新导入。记录不上传到网页，但随代码提交 GitHub；它不是原图备份。删除网站条目也保留处理历史，防止误导入旧照片。

## 已处理照片怎样归档

**可以在满足条件后把原图移出 incoming，后续构建不再需要它。** 前提是对应网页图片、内容数据、处理记录均已推送到 GitHub，数据已引用 assets 中的图片，而且对应 Preview 构建成功。

请让 Codex 先运行只读检查：

`npm run archive-check -- --folder "incoming/photography/本次子文件夹"`

检查会读取实际远端分支，逐张核对网页图内容指纹、处理记录和内容文件。未推送、未处理、网页图缺失或被改动都会阻止归档。检查不会移动、删除或覆盖任何照片。检查通过也不等于你已批准归档；仍需你明确说“批准归档这个文件夹”，或由你手动操作。

建议在项目外使用：

`/Users/mac/Documents/Leo Xiang Art 已处理素材归档/`

内部沿用 `events/日期_地点/`、`photography/日期或专题/`、`art/作品名称/`。这是推荐位置，本轮没有创建目录或搬动原图。你也可以选外置硬盘上的同样结构。建议先复制并核对文件数量和指纹、保留备份，再由你决定是否移走 incoming 中的副本；不要只保留优化网页图，未来打印或重新修图仍需要原图。

在归档批次旁保留：原相对路径、原图 SHA-256、网页图路径、GitHub 提交号及审核过的 Preview 地址。只读检查输出提供前四项中的文件信息与提交号，Preview 地址由 Codex 补充。若整个文件夹还有未用于网站的照片，不按“全部已处理”归档；先向你说明并由你决定另行保存。
